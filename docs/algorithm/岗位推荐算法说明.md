# 岗位推荐算法说明（v2.0）

**适用模块**：`GET /api/v1/recommendations`、`GET /api/v1/recommendations/{jobId}/explain`  
**实现位置**：`RecommendationService` + `MatchEngine` + `SemanticScoringService`  
**相关文档**：`docs/req/岗位匹配功能模块说明文档.md`、`docs/interface/记忆库和岗位匹配模块接口文档.md`

---

## 1. 目标

新算法解决旧版四个问题：

1. **长度偏差**：旧版直接 `SUM(weight × confidence)`，岗位标签越多、JD 越长，分数天然越高。
2. **扣分拍脑袋**：旧版缺失项统一扣 `weight × 0.16`，没有区分必备项/加分项。
3. **分数不可解释**：旧版分数是 1–4 的小数，和原型里“为什么是 87 分”不一致。
4. **无法利用语义**：标签归一化没覆盖的同义表达（如“小红书运营” vs “新媒体运营”）会漏匹配。

新算法把推荐分拆成：

```text
最终分（0–100） = 结构化分（0–85） + 语义分（0–15）
```

- **结构化分**：标签是否命中、技能等级差、必备/加分项覆盖情况，按岗位标签总权重归一化。
- **语义分**：用户画像文本与岗位 JD 的向量余弦相似度，作为辅助分，不能推翻硬过滤。
- **降级**：Embedding 不可用时，结构化分改为 0–100，语义分不返回。

---

## 2. 数据与流程

### 2.1 输入

| 数据 | 来源 |
|---|---|
| 用户正向标签 | `memory_tags` + `memory_items`（`polarity=1`、`status=1`） |
| 用户排除标签 | `memory_tags.polarity=-1` |
| 用户 skill 等级 | `user_skill_profile`（缺失时回退到 `memory_tags.proficiency`） |
| 候选岗位 | `jobs.status=1`（可加 `city`） |
| 岗位标签 | `job_tags` + `tags` |
| 语义向量 | `EmbeddingClient`，模型 `text-embedding-v3`，1024 维 |

### 2.2 流程

```text
加载用户正向/排除标签、skill 等级
        ↓
加载在招岗位 + 岗位标签
        ↓
第一段：排除过滤 → location 硬过滤（+ city 收窄）
        ↓
第二段：结构化分（MatchEngine）
        ↓
语义分（SemanticScoringService，可用时）
        ↓
final = clamp(structured + semantic, 0, 100)
        ↓
排序 → minScore 过滤 → 分页 → 归因
```

---

## 3. 第一段：硬过滤

### 3.1 排除过滤

岗位的任意 `job_tags.tag_id` 命中用户 `polarity=-1` 的标签，整个岗位剔除，记入 `filterSummary.excludedByPolarity`。

### 3.2 location 硬过滤

如果用户有 `category=location` 且 `polarity=1` 的标签：

1. 优先看岗位的 `job_tags` 是否命中用户 location 标签；
2. 如果岗位没有 location 标签（数据缺失），用 `jobs.city` 与用户 location 标签名做兜底匹配；
3. 都不命中则剔除，记入 `filterSummary.excludedByLocation`。

> 设计取舍：`location` 是硬门槛，不参与“用高分弥补城市不符”的软匹配。若产品希望支持“杭州周边/远程”，应扩展为 location 的软硬两级，而不是直接降低权重。

### 3.3 city 参数

`city` 在 SQL 中先收窄岗位池，属于硬过滤之上的额外筛选。被 city 排除的岗位也记入 `excludedByLocation`。

---

## 4. 第二段：结构化分

### 4.1 符号

| 符号 | 含义 |
|---|---|
| `T` | 岗位的全部 `job_tags` |
| `totalWeight` | `Σ weight`，只统计 `weight > 0` 的标签 |
| `semanticAvailable` | 语义服务本次是否可用 |
| `structuredMax` | 语义可用时 85，不可用时 100 |
| `weight` | 岗位标签权重：1.0 必备 / 0.5 加分 |
| `confidence` | 用户标签置信度 0–1 |
| `levelFactor` | skill 等级系数 |

### 4.2 单个标签的贡献

| 场景 | contribution（分） |
|---|---|
| 命中，非 skill 或 `requiredLevel=0` | `structuredMax × weight × confidence / totalWeight` |
| 命中 skill 且 `requiredLevel>0` | `structuredMax × weight × confidence × levelFactor / totalWeight` |
| 未覆盖必备项（weight=1.0） | `-structuredMax × weight × 0.50 / totalWeight` |
| 未覆盖加分项（weight=0.5） | `-structuredMax × weight × 0.25 / totalWeight` |
| 命中用户排除项（仅 explain） | `-structuredMax × weight × 1.0 / totalWeight` |

`levelFactor`：

| 用户 level vs requiredLevel | 系数 |
|---|---|
| 用户 ≥ 要求 | 1.0 |
| 差 1 级 | 0.5 |
| 差 2 级 | 0.2 |
| 差 ≥ 3 级 | 0 |

### 4.3 汇总

```text
structured = clamp(Σ positive + Σ negative, 0, structuredMax)
```

- `positive`：所有正向贡献，写入 `positive` 数组。
- `negative`：未覆盖/排除项，写入 `negative` 数组。
- `gap`：未覆盖的 skill + 等级差 > 0 的 skill，单独给前端展示。
- `matchedTagCount`：正向贡献 > 0 的标签数。

### 4.4 为什么按总权重归一化

假设两个岗位：

- A：8 个标签，用户命中 6 个高质量标签；
- B：3 个标签，用户命中 3 个高质量标签。

旧版 `SUM` 会让 A 天然高于 B；新版用 `Σ contribution / totalWeight` 后，A 缺 2 个标签会被扣分，B 的覆盖率更高，排序更符合“匹配度”而不是“标签数量”。

### 4.5 为什么必备项扣 0.5、加分项扣 0.25

- 必备项没覆盖，说明岗位的核心条件不满足，扣得更重；
- 加分项没覆盖，只是少了一个亮点，扣得轻；
- 这两个值是产品可调参数，放在 `application.properties`，不写死在代码里。

## 5. 语义分

### 5.1 文本构造

用户画像文本（只取正向标签）：

```text
求职者画像：地点：杭州，证据：想留在杭州；偏好：大小周（...）；技能：内容策划（熟练），证据：做了 3 篇小红书笔记...；
```

岗位文本：

```text
岗位：内容运营；城市：杭州；公司：某杭州电商公司；JD：负责品牌内容矩阵...；岗位标签：杭州、内容策划、数据复盘、
```

### 5.2 相似度与归一化

```text
cosine = cosine(userVector, jobVector)
normalized = clamp((cosine - 0.55) / (0.85 - 0.55), 0, 1)
semantic = 15 × normalized
```

- `0.55` / `0.85` 来自 `text-embedding-v3` 在种子数据上的实测：同领域岗位余弦约 0.63–0.81，需要用区间拉开差距。
- 换模型/换领域语料后必须重新标定；这两个值在 `application.properties` 可配。

### 5.3 缓存与降级

- 用户向量：key = `userId`，内容变化用 SHA-256 判断，变化才重新请求。
- 岗位向量：key = `jobId`，JD/标签文本变化才重新请求。
- 首次推荐请求把“用户 + 所有候选岗位”合并成一次 batch（最多 10 条/次），后续命中缓存不再请求。
- Embedding 调用失败：`failure-backoff-seconds` 内所有推荐直接降级为结构化 100 分制，避免每个请求都等 30 秒超时。
- 只缓存向量，不缓存最终分，不新增表；多实例部署时每个实例各自缓存。

### 5.4 降级行为

| 情况 | structuredMax | semanticScore | explain.semantic |
|---|---|---|---|
| Embedding 正常 | 85 | 0–15 | `available=true` |
| 未配置/失败/熔断 | 100 | 不返回 | `available=false`，`message` 说明降级 |

降级时排序只由结构化分决定，保证接口可用性优先。

---

## 6. 最终分与排序

```text
score = clamp(structured + semantic, 0, 100)
```

排序规则：

1. `score` 降序；
2. `structuredScore` 降序；
3. `matchedTagCount` 降序；
4. `semanticScore` 降序；
5. `jobId` 升序（保证稳定）。

`minScore` 在最终分上过滤；`total` 是过滤后的数量；`candidateCount` 是第二段开始前的候选数。

## 7. 种子数据实测

用户 1 的正向标签：杭州、大小周、带教、内容策划、数据复盘、内容排期、用户增长、私域运营、新媒体运营；排除：销售。
候选：J1、J3、J5、J6；J2 因上海被 location 过滤，J4 因销售被排除。

| 岗位 | structured | semantic | score | 说明 |
|---|---:|---:|---:|---|
| J3 内容运营（某杭州电商） | 79.29 | 13.20 | **92.49** | 5 个标签全覆盖，语义最高 |
| J6 新媒体运营（网易） | 75.74 | 11.27 | **87.01** | 技能/经历匹配完整 |
| J1 内容运营（校招，字节） | 33.54 | 10.20 | **43.74** | 缺本科/3-5年/A-B 测试，扣分明显 |
| J5 品牌内容运营（字节） | 11.05 | 7.22 | **18.27** | 缺短视频脚本/品牌活动/本科/3-5年 |

J1 的归因拆分：

```text
positive  = 48.25
negative  = -14.71   （本科 -6.54、3-5年 -6.54、A/B 测试 -1.63）

score      = 43.74
```

> 以上数值是一次实际运行结果；模型/prompt/种子数据变化后会有轻微浮动。

## 8. 配置项

| 配置 | 默认 | 说明 |
|---|---|---|
| `career-trace.match.structured-weight` | 85 | 结构化满分 |
| `career-trace.match.semantic-weight` | 15 | 语义满分 |
| `career-trace.match.required-miss-penalty` | 0.50 | 未覆盖必备项扣分比例 |
| `career-trace.match.bonus-miss-penalty` | 0.25 | 未覆盖加分项扣分比例 |
| `career-trace.match.semantic-floor` | 0.55 | 余弦相似度下限 |
| `career-trace.match.semantic-ceiling` | 0.85 | 余弦相似度上限 |
| `career-trace.embedding.enabled` | true | 是否启用语义分 |
| `career-trace.embedding.model` | text-embedding-v3 | 向量模型 |
| `career-trace.embedding.dimensions` | 1024 | 向量维度 |
| `career-trace.embedding.batch-size` | 10 | 单次批量上限 |
| `career-trace.embedding.failure-backoff-seconds` | 60 | 语义失败熔断 |

## 9. 复杂度与扩展

- 结构化计算：`O(candidateCount × avgJobTags)`，在 Java 内存中完成。
- 语义计算：首次 `O(candidateCount)` 次 embedding（一次 batch），之后命中缓存为 0 次网络请求。
- 当前仍会加载全部在招岗位并在内存排序；岗位量到万级时，建议：
  1. SQL 先用 `jobs.city` + location 标签倒排预筛；
  2. 只对前 N 个候选拉 `job_tags`；
  3. 加 `recommendations` 缓存表（按 user + 过期时间），接口结构不变。
- 多实例部署时，向量缓存和熔断状态不共享；建议后续换成 Redis。

---

## 10. 已知限制

1. **岗位标签质量决定上限**。`job_tags` 缺失 location/必备项时，结构化分会失真；需要离线打标任务保证覆盖率。
2. **语义阈值是经验值**。`0.55–0.85` 只适配当前 `text-embedding-v3` + 中文招聘语料，换模型需重新标定。
3. **同义标签仍可能漏匹配**。语义分能缓解，但不能替代 `tag_aliases` 治理；例如“小红书运营”和“新媒体运营”仍是两个 tag。
4. **缺失项扣分是产品选择**。0.5/0.25 不是唯一答案，应根据“投递转化率”回流数据调参。
5. **seniority 未做硬过滤**。学历/年限目前是扣分项；若产品要求“本科以下直接过滤”，需要在第一段加硬规则。
6. **进程内缓存**。重启后首次请求会重新计算向量；多实例不共享，后续可迁移到 Redis。
7. **未做推荐日志/曝光回流**。`usedInMatchCount` 仍返回 0，等推荐日志表落地后再统计。

## 11. 联调与测试约束

- 单元测试使用假 `DeepSeekClient` / `EmbeddingClient`，不访问外部 API，覆盖：重试 3 次、不可重试错误、语义分计算、缓存命中、语义降级。
- 联调阶段实际调用：
  - Embedding 成功 3 次（单文本连通性、7 文本相似度标定、推荐首请求 batch）；
  - DeepSeek 成功 1 次（新增记忆打标）。
- 均未超过 5 次限制。
