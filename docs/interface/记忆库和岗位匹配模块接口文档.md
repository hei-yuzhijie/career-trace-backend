# 职迹 CareerTrace · 接口文档（记忆库 + 岗位匹配）

**版本**：v0.2  
**基础路径**：`/api/v1`  
**Content-Type**：`application/json`  
**认证**：除特别标注外，均需 `Authorization: Bearer <token>`

> **登录说明**：先调用 `POST /api/v1/auth/login`，后续请求带 `Authorization: Bearer <accessToken>`。
> 本地联调可把 `career-trace.auth.enabled` 改成 `false`，此时使用 `career-trace.auth.dev-user-id`（默认 1）。
> 登录/刷新/登出接口见 [登录认证接口文档](./登录认证接口文档.md)。

## 通用约定

### 统一响应体

```json
{
  "code": 200,
  "msg": "success",
  "data": {}
}
```

| code | 含义 |
|---|---|
| 200 | 成功 |
| 400 | 参数错误 |
| 401 | 未登录 / Token 失效 |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 409 | 资源冲突（如重复提交） |
| 500 | 服务端异常 |

### 分页参数

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| page | int | 1 | 页码，从 1 开始 |
| size | int | 10 | 每页条数，最大 50 |

### 分页响应

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "total": 42,
    "page": 1,
    "size": 10,
    "records": []
  }
}
```

# 一、记忆库接口

## 1.1 新增记忆

`POST /api/v1/memories`

**说明**：写入 `memory_items` 后，**异步任务**调用大模型抽取标签、归一化、写 `memory_tags`。接口立即返回 `memoryId` 和 `taggingStatus=PENDING`。

**请求体**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| content | string | 是 | 记忆原文，长度 1–2000 |
| sourceType | string | 是 | `resume` / `interview` / `manual` / `review` |
| sourceId | long | 否 | 来源对象 ID，如简历 ID |

```json
{
  "content": "想留在杭州，能接受大小周，希望有带教",
  "sourceType": "manual"
}
```

**响应**

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "memoryId": 101,
    "taggingStatus": "PENDING",
    "estimatedSeconds": 8
  }
}
```

**备注**

- `content` 超过 2000 字返回 `400`。
- 同一用户 10 秒内重复提交相同 `content` 返回 `409`（防抖）。
- 打标完成后可通过 `GET /memories/{id}/tags` 查询结果。
- 打标调用大模型最多尝试 **3 次**（首次 + 2 次重试）；仅超时、限流、5xx、解析失败等可重试错误会重试，鉴权/参数错误不重试。
- 提示词与输出约束维护在 `src/main/resources/prompts/memory-tagging.md`，不硬编码在 Java 中。

## 1.4 更新记忆原文

`PUT /api/v1/memories/{memoryId}`

**说明**：只改原文，**不自动重打标签**。如需重打，显式调用 `POST /memories/{id}/retag`。避免用户改一个错字就触发全量打标。

**请求体**

```json
{
  "content": "想留在杭州，能接受大小周，希望有带教老师"
}
```

**响应**

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "memoryId": 1,
    "updatedAt": "2026-11-09 15:01:00",
    "needRetag": true
  }
}
```

**备注**

- 原 `memory_tags` 保留不变，`needRetag=true` 提示前端显示“原文已改，是否重新分析？”按钮。
- 用户确认后调 `POST /memories/{id}/retag`。

## 1.5 删除记忆（软删除）

`DELETE /api/v1/memories/{memoryId}`

**说明**：置 `memory_items.status=0`，同时**删除该记忆关联的 `memory_tags`**（否则推荐会读到孤立标签），并触发 `user_skill_profile` 异步重算。

**响应**

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "memoryId": 1,
    "deleted": true,
    "skillProfileRecalc": "ASYNC"
  }
}
```

# 二、岗位匹配接口

## 2.1 获取推荐岗位（核心）

`GET /api/v1/recommendations`

**说明**：两段式 + 语义混合匹配。

1. **第一段（硬过滤）**：剔除包含用户 `polarity=-1` 标签的岗位；若用户有 location 标签，岗位必须命中至少一个 location 标签（岗位没有 location 标签时，用 `jobs.city` 与用户 location 名称兜底）；`city` 参数在硬过滤之上再收窄。
2. **第二段（结构化 + 语义）**：结构化分 0–85（按岗位标签总权重归一化），语义分 0–15（用户画像文本与岗位 JD 的向量余弦相似度），最终分 0–100。

**Query 参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| page | int | 否 | 页码 |
| size | int | 否 | 每页条数 |
| city | string | 否 | 额外城市筛选（在 location 硬过滤之上再收窄） |
| minScore | number | 否 | 最低分过滤，默认 0，范围 0–100 |
| explain | boolean | 否 | 是否返回归因明细，默认 `true` |

> 示例中的 `reasons` 只列出部分归因项，`contribution` 为四舍五入后的示意值；实际数值以本节“计分口径”与 `docs/algorithm/岗位推荐算法说明.md` 为准。

**`records[]` 计分字段**

| 字段 | 说明 |
|---|---|
| score | 最终分 0–100 = structuredScore + semanticScore |
| structuredScore | 结构化分；语义可用时满分 85，语义不可用时满分 100 |
| semanticScore | 语义分 0–15；语义不可用时字段不返回 |
| matchedTagCount | 命中的正向标签数（不含未覆盖/排除项） |

**`filterSummary` 字段说明**

| 字段 | 说明 |
|---|---|
| excludedByPolarity | 被用户排除项过滤掉的 jobId 列表（如 `[4]` 销售岗） |
| excludedByLocation | 被 location 硬过滤掉的 jobId 列表（如 `[2]` 上海岗） |
| candidateCount | 进入第二段加权计算的岗位数 |

**计分口径**

设：

- `totalWeight = Σ job_tags.weight`（只统计 weight > 0 的岗位标签）
- `semanticAvailable`：语义服务是否可用
- `structuredMax = semanticAvailable ? 85 : 100`

单个岗位标签的贡献：

| 场景 | contribution（分） |
|---|---|
| 命中（非 skill 或 requiredLevel=0） | `structuredMax × weight × confidence / totalWeight` |
| 命中 skill 且 requiredLevel>0 | `structuredMax × weight × confidence × levelFactor / totalWeight` |
| 未覆盖的必备项（weight=1.0） | `-structuredMax × weight × 0.50 / totalWeight` |
| 未覆盖的加分项（weight=0.5） | `-structuredMax × weight × 0.25 / totalWeight` |
| 命中用户排除项（仅 explain 展示） | `-structuredMax × weight × 1.0 / totalWeight` |

`levelFactor`：

| 用户 level vs 岗位 requiredLevel | 系数 |
|---|---|
| 用户 ≥ 要求 | 1.0 |
| 差 1 级 | 0.5 |
| 差 2 级 | 0.2 |
| 差 ≥ 3 级 | 0 |

最终分：

```text
structured = clamp(Σ positive + Σ negative, 0, structuredMax)
semantic   = 15 × clamp((cosine - 0.55) / (0.85 - 0.55), 0, 1)   // 语义可用时
score      = clamp(structured + semantic, 0, 100)
```

**备注**

- 结构化分按岗位标签总权重归一化，避免“标签多、JD 长”的岗位天然高分。
- 岗位的 seniority 类标签（本科、3-5 年）同样参与结构化分，`category` 返回 `seniority`，没有 `levelFactor`。
- 若用户**没有任何 location 标签**，跳过 location 硬过滤，全部在招岗位进入候选集。
- 若用户**没有任何正向标签**，返回空列表并提示“请先补充职业记忆”。
- 语义服务不可用时：`structuredMax=100`，`semanticScore` 不返回，`score` 只由结构化分决定；`explain` 中 `semantic.available=false`。
- 语义结果按内容 hash 缓存在进程内，不新增表；Embedding 失败后默认 60 秒内降级，避免每个请求都等待超时。
- 推荐仍是**实时计算**，不读 `recommendations` 缓存表；进程内只缓存向量，不缓存最终分数。

**错误**

| code | 场景 |
|---|---|
| 400 | 分页参数非法 |
| 401 | 未登录 |

**备注**

- `positive` / `negative` 的 `contribution` 是**分数**（0–100 分制下的贡献分），不是 0–1 权重；`positive + negative` 再截断即为 `structured`。

- 该接口**实时计算**；语义向量按内容 hash 缓存在进程内，不读最终分数缓存，不新增表。
- `explain=false` 时列表不返回 `reasons`，但为了算分仍会计算结构化分和语义分。

# 四、两个设计上的提醒

**① 记忆更新与打标解耦。** `PUT /memories/{id}` 只改原文、不自动重打标，靠 `needRetag=true` 让用户决定。否则用户改个错别字就触发一次大模型调用，成本不可控。

**② 推荐接口的 `explain` 参数要保留。** 前端列表页可能只需要 `score` 和 `matchedTagCount`，归因明细在点开详情时才拉。`explain=false` 时后端跳过 `reasons` 组装，能省一次 `memory_tags` 回查。这是你原型里“列表轻、详情重”的直接体现。

**③ 推荐是实时算的，不是读缓存。** 第一版 `filterSummary` 和 `reasons` 都在一次请求内算完。如果以后加 `recommendations` 缓存表，这个接口的响应结构不用变，只是数据来源从实时 SQL 换成读缓存 + 过期重算。
